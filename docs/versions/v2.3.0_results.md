System: double_integrator. Axis: replay-buffer recency (per-buffer FIFO sliding window).
SOTA of record entering v2.3.0: DI cps 0.8568 (v2.0.1, seed 42, n2000 @ goal_speed_radius 0.30).
Eval standard: full n2000 / seed 23456, goal_speed_radius 0.30, n2000 re-selection over the

## Part I — what was tested

Motivation: the v2.2.2 close found the collection/replay buffer never evicts before step 1M
(buffer_cap 1,000,000 trajectories, episodes_per_collect = collect_every = 100), so every run
samples its entire training history uniformly; fresh on-policy data is 0.1-0.24% of each batch.
A per-buffer cap was added (policy_buffer_cap, D_pi only; flag-off bit-identical) so D_pi can be
shrunk to a sliding window without touching D_V or the precursor buffer. Plain DI, injection OFF
(single axis = policy_buffer_cap). Code + smoke in dpi_policy_buffer_window.md.

## Part II — buffer-recency results (single-seed, seed 42)

| config | budget | n2000 cps @0.30 | 95% CI | vs SOTA 0.8568 | collapse |
|---|---|---|---|---|---|
| D_pi=5k, D_V=1M | 42k | 0.8702 | [0.8495, 0.8904] | +0.013 (tie) | no |

Findings:
1. D_pi recency saturates. 5k vs 2k differ by 0.0002 — shrinking the policy buffer further does
   not move cps. If buffer size were the binding constraint, the response would be monotone; it
   is flat. (K_pi=1 vs K_V=3 — the policy side takes fewer updates per macro step, limiting the
   surface on which D_pi staleness can act.)
2. D_V recency is collapse-safe but slightly negative. Shrinking D_V to a 10k window (the
   higher-risk lever — D_V's stale unsafe trajectories are the V-collapse guard, and with
   injection OFF the only backstop is adaptive sigma) did NOT trigger collapse (probe_h_mean
   -0.90 -> -0.59 stable, sigma at the 0.30 floor essentially the whole run, rho_unsafe_v ~0.2 >
   target). But it cost -0.0227 vs D_V=1M — consistent with D_V's value being unsafe-signal
   coverage, not freshness.
3. No configuration is a confirmed SOTA beat — all CIs include 0.8568, the same standing as
   v2.2.2's 0.8607. The collapse-safety hypothesis (D_V untouched -> no collapse) held in every
   run, and even held when D_V was shrunk.
4. cps was capped by HardNet projection infeasibility (0.07-0.33 oscillating), NOT collisions
   (0.0075-0.0095) and NOT navigation (reach ~0.95). This redirected the investigation to
   collection coverage (Part III).

## Part III — collection coverage audit and the admission unit-bug

The buffer-size axis being saturated, a read-only audit (collection_audit.md) mapped what states
get collected. Two results matter for the path forward:

1. F1 is a closed lever. The one feasibility-shaping loss (cbf_deriv_feasibility_loss) was the
   primary axis of v2.2.1: it lifted ||L_g h|| as designed but did not move cps, because it
   targets only the ~33% control-authority slice of the collision budget; the dominant ~67% is
   calibration under-coverage (V_S sees danger too late). Recorded rejected in v2.2.1. Not a
   candidate again.

2. The start-state admission filter has a unit-bug (the F2 thread). The "unavoidable-collision"
   filter is meant to reject a start only if braking at max deceleration u_max toward the
   nearest obstacle still collides. The implemented inward_speed is
   dot(unit(velocity), center_delta) — a projected DISTANCE (m), not the projected SPEED (m/s)
   the criterion needs (scene_init.py:244,255). It ignores approach speed entirely and scales
   with distance. Verified: "uses a distance proxy in the speed slot -> does not implement the
   intended max-braking criterion."

   Offline pool check (CPU, frozen .pkl): under the CORRECT criterion, 0 of 2500 eval scenes
   (n2000 + n500) are unavoidable-collision. The pools are clean — but because a separate floor
   dominates the bug (min clearance 0.15 m > max physical braking distance ~0.12 m at
   v_init_max=0.5), NOT because the buggy term works. Corollary: the infeasibility cap reflects a
   genuine filter/value limit on RECOVERABLE states, not poisoned/doomed starts.

   Consequence: the bug is real but inert at v_init_max=0.5 (the clearance floor masks it). It
   activates only once start speeds exceed the floor — which is exactly what raising v_init_max
   would do. This sets the v2.3.1 plan: fix the admission physics (B), then raise v_init_max (A)
   to actually generate fast-approach states. Carried to v2.3.1.

## Experiment: u_max widening (2 → 20)

Full input-limit removal (disable_box=true) was attempted first but joint training failed to
converge under it; u_max=20 is the relaxed re-training that did converge, chosen to observe how
performance responds when the input constraint is relaxed even if such an actuator bound is
physically unrealistic.

System: double_integrator. User-directed experiment: **widen the actuator bound `u_max` from
2.0 to 20.0** on the v2.3.0 SOTA configuration; everything else identical. Fresh 100k-step
seed-42 run (not warm-started). This is an EXPERIMENT row, **not a SOTA promotion** — see the
verdict.

Run dir: `data/previous_runs/v2.3.0_umax20__20260628-212951__seed42/`
(checkpoints, eval CSVs, figures, config.yaml, logs, and `source_changes.patch`).

### TL;DR / verdict

- n2000/seed23456 eval on `best.pt` (step 72,000): **cps 0.9419 [0.9290, 0.9551]** vs v2.3.0
  SOTA **0.8700** (seed-42 adopted; 3-seed mean 0.8698).
- The single change was `u_max 2 → 20`, which raises the actuator bound **globally** (policy
  output range, LQR clamp, RK4 dynamics, and the HardNet projection box are ALL ±20). It is
  **not** "remove the box from the projection" (that is `disable_box=true`, implemented in code
  but left OFF here).
- **SOTA UNCHANGED.** The +0.072 cps is mostly a *different, easier problem* (≈10× acceleration
  authority) plus the ±20 box almost never binding — not a like-for-like improvement, and not
  deployable on ±2 actuators.

### Part I — what was run

- Baseline: v2.3.0 effective config (D_pi=2k / D_V=1M, injection OFF, goal_speed_radius 0.30,
  v_init_max 0.5, n_steps 100k, schedule_n_steps 42k). Per-component-uniform DI start sampler
  (v2.3.0, NOT the v2.3.1 magnitude+angle sampler). Verified the run was on the v2.3.0 commit
  (`git_commit.txt` = `8dbda0c DIRTY`).
- **Single functional change:** `env.bounds.double_integrator.u_max: 2.0 → 20.0`.
  - Note `v_max` stays **2.5** (speed is still clamped by `wrap_state`), so the robot is not
    faster — it can only *accelerate/brake/turn ~10× harder*.
  - `filter.hardnet.disable_box` was added to the code (gated flag) but set **false**; the
    box-aware projection runs normally, now against the ±20 box.
- Trained to 100k (no halt, no NaN). In-loop best cps 0.9756 @ step 72,000 (n500/seed12345).
  `best.pt` = step 72,000; `final.pt` = step 100,000 (not separately n2000-evaluated).

### Part III — mechanism (why cps rose)

Two confounded effects, both expected:

1. **≈10× acceleration authority.** With `u_max=20` the policy/LQR can brake, turn, and
   correct far more aggressively while still capped at `v_max=2.5`. This directly explains the
   navigation gains: stuck 0.026→0.001, timeout 0.020→0.012, reach 0.947→0.98. The control
   problem is simply easier.
2. **The ±20 box almost never binds.** This session's box-vs-CBF attribution diagnostic
   (on the v2.3.0 SOTA, n2000) decomposed the deployed infeasibility **0.088 = singular
   (‖L_g h‖<5e-4) 0.059 + box-induced (CBF∩box empty) 0.029**, and showed the CBF-only
   (unbounded) action exceeds ±2 in only ~1.65% of steps with peaks ~|u|≈90–500 at
   near-singular states. Widening the box to ±20 removes essentially all of the box-induced
   term, so infeasibility falls 0.088→0.062 ≈ the singular floor. (Consistent with that
   diagnostic: 0.062 ≈ 0.059 singular.)

So `u_max=20` is, in effect, a *regularized proxy* for "no projection box" — it removes
box-binding without the `disable_box=true` blow-up (where the un-clamped base projection
spikes to |u|≈500 at ‖L_g h‖→0). The true `disable_box=true` experiment was NOT run.

### Part IV — caveats / what this is NOT

- **Not a SOTA improvement.** Different actuator spec (±20 vs ±2). The comparison answers
  "does 10× more control authority help?" (yes, trivially), not "is the method better."
- **Not deployable on ±2 hardware.** Executed actions routinely use |u| up to 20.
- **Not the requested "box removed from projection" run.** That is `disable_box=true` with
  `u_max=2` (project onto the CBF half-space alone, no clipping). Implemented in code
  (`source_changes.patch`) but unused here. Likely unstable as-is (the |u|≈500 singular
  spikes); would need e.g. `lg_reg_eps>0` or a milder regularizer.
- **Single seed (42); `best.pt` (in-loop best @72k), NOT n2000-reselected.** v2.3.0 SOTA
  numbers use top-8 in-loop n2000 re-selection; best.pt is selection-biased/noisier. For a
  fair number, re-select over the top-8 in-loop checkpoints on n2000.

### Part V — open questions / how to use this

For future sessions deciding whether to pursue this axis:

1. **Is ±20 a legitimate target, or a diagnostic?** If the deployment hardware genuinely
   allows ~±20 accel, this is a real, large win and worth multi-seed confirmation. If the
   actuator limit is physically ±2, this run is only a diagnostic (control authority is the
   binding constraint, not the method).
2. **Disentangle the two effects.** Run a `u_max` dose-response (e.g. 2, 4, 8, 20) at fixed
   seed to separate "accel authority" from "box-binding removal." If cps rises smoothly with
   u_max, it is dominated by authority; if it jumps as soon as the box stops binding (small
   widening), it is the box term.
3. **The honest box-removal test** is `disable_box=true, u_max=2` — needs a stability fix for
   the singular-state spikes. That, not u_max=20, isolates "CBF half-space only."
4. **If promoting any of this:** multi-seed (3+) + n2000 re-selection, and record it under a
   distinct actuator spec (do not compare against the ±2 SOTA as if equal).
